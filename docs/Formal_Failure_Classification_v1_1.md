# 正式实验失败分类与 API 失败处理协议 v1.1

修订日期：2026-08-25

本补充协议用于修正正式实验结束门禁中对 `failed` 的解释方式。本次修订不改变模型、Prompt、Agent 调度、工具、题库、天气快照、铁路快照、预算公式、金标或独立评价指标，只修正实验基础设施中的失败分类、门禁判断和最终归档顺序。

## 1. 修订原因

中转 API 在完整运行中可能出现可追踪的偶发 429、5xx、连接错误或请求超时。原门禁把模型方法失败、API 基础设施失败和实验完整性失败全部混成一个 `failed`，会导致两类问题：

- 模型格式错误或回答错误本来应该保留并计为方法成绩的一部分，却会被误判为整轮实验作废；
- API 基础设施事故和实验文件损坏没有被区分，论文无法透明说明失败来源。

因此，正式实验必须先分类，再决定是否阻塞论文结论。

## 2. 三类失败

### A. 方法失败

满足以下特征：

- API 调用成功；
- 模型确实返回了内容；
- 原始回答和 trace 已保存；
- 但输出格式不合法、缺少字段、违反约束或任务回答错误。

处理规则：

- 必须保留；
- 不得删除或单独重跑到成功；
- STSR 记为 0；
- 继续放在主分析分母中；
- 不导致整轮实验完整性门禁失败。

### B. API 基础设施失败

满足以下特征：

- HTTP 429、5xx；
- 网络连接错误；
- 请求超时；
- 已执行正式协议规定的最多 3 次尝试；
- 最终仍没有获得可用模型回答，或内部 Agent 调用发生终止性 API 事故。

处理规则：

- 每次 LLM 调用最多 3 次尝试，即首次调用加最多 2 次重试；
- 429、5xx、连接错误和请求超时允许重试；
- 三次均失败后，不允许只补跑该题；
- 失败结果和重试轨迹必须保留；
- 如果 API 失败导致整条方法结果失败，主分析中 STSR 记为 0；
- 如果内部 Agent 发生终止性 API 事故，但系统仍完成最终答案，则保留最终实际评分，同时记录 API 事故。

论文必须报告：

- 总 LLM 调用数；
- 重试次数；
- 重试后恢复次数；
- 终止性 API 失败次数；
- 受影响的结果数量。

### C. 实验完整性失败

包括：

- 缺少计划中的结果；
- M0～M3 方法组合不完整；
- 重复结果；
- 缺少 trace；
- 使用 mock 或 fallback；
- 题库、代码、数据哈希不一致；
- worker 异常且没有保存失败行；
- 最终文件损坏。

处理规则：

- 这类失败阻塞正式实验门禁；
- 不能通过 STSR 记 0 掩盖；
- 如果无法离线恢复，必须完整重跑新一轮实验。

## 3. 正式统计方式

### 主分析：意向性分析

所有 CTP100 评价单元都保留：

- 方法格式失败记 0；
- 方法质量失败记 0；
- API 导致整条方法结果失败也记 0；
- 不删除任何失败案例。

### 敏感性分析：排除 API 污染

针对 M3 与 M2 的主比较，额外计算一次无 API 污染配对分析：

- 只排除 M2 或 M3 存在终止性 API 基础设施事故的配对评价单元；
- 模型回答错误、格式错误、约束错误不能排除；
- 重新报告 M3 与 M2 的 STSR 差值、95% bootstrap 置信区间和 McNemar 检验 p 值；
- CTP100 主实验中，无 API 污染的 M2/M3 有效配对数不得低于 95。

如果主分析和敏感性分析方向一致，论文结论更可信；如果方向不一致，论文必须如实讨论 API 稳定性对结论的影响。

## 4. 新正式门禁

原先过于笼统的门禁：

```text
no_failed_results
api_failure_timeout_count_zero
```

改为：

```text
all_planned_results_saved
all_failures_classified
all_api_failures_have_retry_evidence
all_api_failures_retained
no_missing_results
no_duplicate_results
no_mock_or_fallback
no_integrity_failures
sensitivity_analysis_available
```

其中，方法失败和 API 基础设施失败是实验事实；实验完整性失败才会阻塞论文级结论。

## 5. 最终归档顺序

正式实验结束后，文件生成顺序固定为：

```text
1. 保存全部方法结果
2. 生成 evaluation_summary
3. 生成 formal_gate
4. 生成 paper_analysis
5. 生成 paper_result_pack
6. 生成 paper_draft_pack
7. 生成 paper_submission_pack
8. 最后一次更新 experiment_manifest
9. 生成 final_artifact_index.json
10. 此后不再修改正式文件
```

`final_artifact_index.json` 记录最终正式文件、trace 和 worker 请求/响应文件的哈希，但不记录自身哈希，避免循环引用。
